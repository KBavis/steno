## ba-04: What happens at the end of each month?

**Expected:** A @Scheduled job (cron "0 55 23 L * ?": 23:55 on the last day of the month, ScheduledTasksConfig.generateBudgetPerformance) runs BudgetPerformanceService.runGenerateBudgetPerformanceJob: for every user, it computes the month's budget overviews (needs, wants, investments, general) and saves them as budget performance rows.

**Key facts:** @Scheduled, last day of the month, generateBudgetPerformance, budget performance

### steno: 5 tool calls, 6 turns, $0.27, 28.6 s

Key facts missing: none

At the end of each month, **budget-app** runs one scheduled job that takes a snapshot of every user's budget performance for that month. It is the only scheduled flow in the system.

## Trigger
`ScheduledTasksConfig#generateBudgetPerformance()` in `backend/src/main/java/com/bavis/budgetapp/config/ScheduledTasksConfig.java:25-30`
- `@Scheduled(cron = "0 55 23 L * ?")` fires at **23:55 on the last day of every month** (`L`). No zone is set, so it uses the server's default timezone.
- It calls `BudgetPerformanceServiceImpl#runGenerateBudgetPerformanceJob(null)`. Passing `null` makes it use the current month and year (`BudgetPerformanceServiceImpl.java:72-129`).

## What it does, for each user in `budget_user`
1. **Skips users who already have a snapshot.** If a `budget_performance` row already exists for this user and month, the user is skipped. This means a second run won't overwrite results from an earlier run or from the admin `POST /budget/performance`.
2. **Loads the user's categories as they stood on the last day of the month** (`CategoryServiceImpl#findAllEntities`, which reads `category` and `category_vt`).
3. **Builds four budget overviews** (`generateBudgetOverviews`, lines 194-264): GENERAL, NEEDS, WANTS and INVESTMENTS. Categories are grouped by their category type's name. For each group it calculates:
   - `totalAmountAllocated`: the sum of the categories' budget amounts.
   - `totalSpent`: the sum of the month's transactions in those categories (from `transaction`, filtered to that month and year).
   - `totalPercentUtilized`: spent ÷ allocated, rounded to 2 decimals.
   - `savedAmountAttributesTotal`: allocated − spent.
   - `totalAmountSaved` (`calculateTotalAmountSaved`, lines 278-302): the category type's own budget amount minus spent. For GENERAL, it uses the sum of all the user's category types instead (`category_type` / `category_type_vt`).
4. **Rebuilds the per-category stats** (`MonthlyCategoryPerformanceServiceImpl#generateMonthlyCategoryPerformances`, `MonthlyCategoryPerformanceServiceImpl.java:61-107`):
   - First it deletes any existing `monthly_category_performance` rows for that user and month (lines 50-59).
   - Then it writes one row per category with: allocation, total spend, utilization, transaction count, top three merchants, and category type ID.
5. **Saves the results.** All the new `BudgetPerformance` records are saved together into `budget_performance` with `saveAllAndFlush`.

## Where the results are read
- `budget_performance` is read by `GET /budget/performance` and `GET /budget/performance/all`.
- `monthly_category_performance` is read by `POST /category/performance` and `POST /category/performance/{categoryTypeId}`.
- The same job can be run by hand through `POST /budget/performance` (admin only) and `POST /budget/performance/recalculate`.

## Things to watch
- **One bad category can stop the whole month's snapshot.** The job runs as a single transaction (`@Transactional`). `generateMonthlyCategoryPerformances` throws a `RuntimeException` when any category has a budget of 0 or less. When that happens, the whole run rolls back and no user gets a snapshot that month.
- **Transactions after 23:55 are missed.** Anything posted between 23:55 and midnight on the last day, or synced later, isn't counted unless someone triggers the recalculate endpoint.

At **11:55 PM on the last day of every month**, the backend runs a scheduled job that takes a snapshot of each user's budget performance for that month. That is the only scheduled task in the backend.

**Trigger:** `ScheduledTasksConfig.generateBudgetPerformance()` uses `@Scheduled(cron = "0 55 23 L * ?")`. Spring's `L` means the last day of the month, and the time follows the server's default timezone. It calls `BudgetPerformanceService.runGenerateBudgetPerformanceJob(null)` (`backend/src/main/java/com/bavis/budgetapp/config/ScheduledTasksConfig.java:25`).

**What the job does** (`BudgetPerformanceServiceImpl.runGenerateBudgetPerformanceJob`, `service/impl/BudgetPerformanceServiceImpl.java:74`):
1. Because no month is passed in, it uses the current month and year.
2. It loops over every user (`userService.readAll()`). A user who already has a `BudgetPerformance` row for that month is skipped, so the job is safe to run twice.
3. For each remaining user:
   - It loads their categories as they stood on the last day of the month (`categoryService.findAllEntities(user, asOfDate)`).
   - `generateBudgetOverviews` builds four `BudgetOverview`s: **GENERAL, NEEDS, WANTS, INVESTMENTS**. Each one has the amount budgeted, the amount spent (that month's transactions in those categories), percent used, and amount saved. Saved means the category type's budget minus what was spent, or for GENERAL, all category types' budgets minus total spend.
   - `MonthlyCategoryPerformanceService.generateMonthlyCategoryPerformances` (`service/impl/MonthlyCategoryPerformanceServiceImpl.java:63`) first deletes any existing rows for that user and month. It then saves one `MonthlyCategoryPerformance` per category: budget, spend, percent used, transaction count, and the **top 3 merchants** by spend (each with total, count, average amount and logo URL).
4. It saves all the `BudgetPerformance` entities together with `saveAllAndFlush`. They're keyed by `BudgetPerformanceId` (month/year + userId).

**Related ways to run the same work:**
- `POST /budget/performance` with a `MonthYear` body runs the same job for any month you choose (`controller/BudgetPerformanceController.java:46`).
- `recalculateUserBudgetPerformance` deletes and rebuilds the snapshot for the logged-in user only.

**Things worth knowing:**
- **Late transactions are left out.** Anything dated after 11:55 PM, or synced after the job runs, is missing from the snapshot. It only shows up if someone recalculates or re-runs the job for that month. Because users who already have a snapshot are skipped, the POST endpoint won't refresh them.
- **One bad category can stop the whole run.** If any category's budget is ≤ 0, `generateMonthlyCategoryPerformances` throws `RuntimeException` (`MonthlyCategoryPerformanceServiceImpl.java:81`). The job is one `@Transactional` method, so this most likely rolls back the snapshot for **every** user that month, not just the one with the bad category.
