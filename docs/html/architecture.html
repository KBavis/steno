Steno · how it fits together · October 2026

Two processes, two databases, one queue

Steno runs as an API process that people and agents talk to, and a worker process that does ingestion. They never call each other. They meet in Postgres, where the API leaves a job row and the worker picks it up, and in Neo4j, where the worker writes the graph and the API reads it back.

This page describes the code as it is on main today, not the full design. Numbers come from job 1 in the local database (Steno ingesting its own repository, commit ff59ac5).

02Each part

What each one is responsible for, where it lives, and how much of it exists.

Browser UI built

Onboarding (organization → spaces → connectors → repositories), a Jobs list that polls job status, and the Visualize tab that zooms from organization to flow.

frontend/src/pages/* · /api proxied to :8000

Admin API built

CRUD for the declared structure, and POST /api/jobs, which only inserts a queued row. It never runs ingestion itself.

backend/src/steno/api/routes/*

Graph views built

Turns Neo4j into one layer at a time: overview, space, application (architecture or code), flow, node detail, search. The same views are meant to back MCP get_node.

backend/src/steno/graph/views.py

MCP server ping only

Mounted in the API process at /mcp, stateless. The first real tools (D54: get_node, get_flow, find_dependents, search, view_flow_code) aren't written yet.

backend/src/steno/mcp/server.py

Worker built

A loop: claim the oldest queued job, run eight stages in order, mark the job succeeded or failed. One job at a time per process; run more processes for parallelism.

ingestion/worker.py · queue.py · pipeline.py

Rule engine + symbol resolver built

Runs rule packs over the clone (ast-grep), asks the Python symbol resolver what names and types mean, and assembles clues into complete facts. Everything stays in memory for the job.

extraction/* · resolvers/python.py · assemblers/*

Graph builder + writer built

Builds a plan of nodes and edges with stable IDs (structure, call graph, one flow per entry point, rollups), then MERGEs it into Neo4j and deletes this repository's stale facts.

graph/build.py · graph/writer.py · graph/ids.py

Rule packs Python only

9 Python packs, 22 rules, each with test cases. The three Java packs have a pack.yaml but no rules yet.

rule-packs/python/* · rule-packs/java/*

Postgres built

Holds the declared structure and the job log, and acts as the work queue (SELECT … FOR UPDATE SKIP LOCKED, no broker). Schema via Alembic.

db/models.py · db/migrations/

Neo4j built

One database: architecture nodes and code nodes. A uniqueness constraint on id per label and a full-text index on :Searchable. No vector index yet (the embedding model is still Open).

graph/schema.py · make graph-init

resolver-jvm not wired

The JavaParser helper builds with Gradle, but nothing in the pipeline calls it yet. The deps stage, which would fetch JARs for it, always skips.

resolver-jvm/

Jev and the LLM not built

Stand-ins and LiteLLM are the plan (D52). Today no decision model or LLM is called anywhere, so every dry run is fully deterministic.

decisions/base.py (interface only) · llm/

03Where data lives

Four places, with very different lifetimes. Knowing which one holds a thing is most of debugging.

PlaceHoldsLivesWritten by
PostgresThe organization, spaces, connectors, repositories (with clone URL and space), every job and one row per stage with its timings and countsPermanentAPI (config, new jobs), worker (claims, stages, status)
Neo4jThe graph: Organization, Space, Repository, Module, File, Function, Application, Interface, Flow, Entity, Table, DataStore, ExternalSystem, and the edges between themUntil the next run of the same repository replaces its factsWorker (write stage); API (org and space projection)
MemoryThe resolver index, every extracted fact, the call graph, the graph planOne jobWorker
DiskThe clone at /tmp/steno-workspaces/job-N/ and the facts file job-N-facts.jsonClone: one job. Facts file: until you delete itWorker

Postgres defines more tables than the code uses. coverage_item, fact_change, job_commit, llm_call, llm_output, jev_decision, tool_call, glossary_term, rule_pack and repository_rule_pack exist in the schema, but nothing reads or writes them yet. Which packs ran is decided fresh in every job and recorded only in the parse stage's metrics.

No facts go to Postgres

The graph lives only in Neo4j and the review copy only in the facts JSON file. Postgres gets counts and timings. That matches D36 (Neo4j is rebuildable from Postgres plus git): rerunning the job rebuilds it.

06Reading the graph back

The Visualize tab never shows Neo4j directly. Every screen is a view computed by GraphViews and laid out in the browser.

EndpointShowsHow it's computed
/graph/overview, /graph/spaceOne level of the containment tree and the links between its childrenLoads the whole containment tree and every effect edge, then rolls each deep node up to the child of this level that contains it
/graph/applicationAn application's interfaces, flows, tables, outbound targets (or, with layer=code, its modules and files)Queries around one Application node; groups endpoints by resource such as /api/jobs
/graph/flowA flow as steps, in the order they run, with what each step reads and writesRe-walks INVOKES from the entry function (up to 12 hops), sorts calls by seq, hides non-significant helpers but follows their calls
/graph/nodeOne node's properties, provenance, and a link to the source line at the ingested commitOne node plus its edges; the link is built from the repository's clone URL
/graph/searchName matchesThe searchable_text full-text index

So a flow on screen is two computations: the builder decided which functions belong to a flow (and stored a functions count on it), and the flow view walks the call graph again to draw it. Steps aren't stored as Step nodes yet; the view derives them from INVOKES every time.

07When the graph looks wrong

Something odd on screen came from one of six places. Walk down the list and stop at the first one where it's already wrong.

  1. SourceIs it really in the code at that commit?/graph/node source link
  2. FactsDid a rule match, or get dropped, and why?job-N-facts.json
  3. Stage countsDid the numbers jump between parse, extract, assemble, flows, write?ingestion_stage.metrics
  4. GraphIs the node or edge in Neo4j, with the right ID?Neo4j Browser :7474
  5. View JSONDid the view roll it up, hide it, or merge it?/api/graph/*
  6. LayoutIs it in the JSON but drawn badly?components/graph/

Steps 1–4 are ingestion problems. Steps 5–6 are visualization problems. The facts file is the most useful single artifact: every node, edge, clue and entry point with the rule and line that produced it, plus every match that was dropped and the reason. You can produce it without a database:

cd backend
uv run steno extract ~/projects/contextualized --json out.json   # parse, extract, assemble only

A working copy is fine now

File discovery used to walk into node_modules and .venv before filtering them out, once per rule: 3.5 minutes on Contextualized's working copy (59,000 files). Parse now lists the files once and never enters skipped folders, so the same working copy takes about 7 seconds.
