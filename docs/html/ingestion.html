How a repository becomes a graph

This page follows one ingestion job through every stage, and separates the parts that are easy to blur together: ast-grep, rules, rule packs, the rule engine, the symbol resolver, and the assemblers.

Every example is real output from running Steno on Contextualized at commit ac93a3b: 112 Python modules, 486 functions, 9 rule packs, 33 endpoints, 33 flows.

01Who does what

Eight parts. The first three are data you write; the rest are code that runs.

Graph builder, writerTurn facts and the call graph into nodes and edges with stable IDs, then save them in Neo4jFiling the cards into the archivegraph/build.py, graph/writer.py

Resolve and assemble are different jobs

  • Resolve means answering what is this?: which symbol a name refers to, a value's type, the constant it holds. Only the symbol resolver (PythonResolver, one per language) does it. It's built once at the start of parse and asked questions until flows ends.
  • Assemble means combining clues from different files into complete facts. Assemblers (assemble.py, the assemble stage) do it, one per clue type and the same for every language. For the hard parts they ask the symbol resolver.

Config placeholders and DI belong to the symbol resolver; stable IDs, stubs and internal vs. vendor hosts belong to the graph builder. There's no other "resolver" (DESIGN_DOC D56).

No part is called an "extractor" (DESIGN_DOC D57). The units are rules in rule packs, the rule engine runs them, and extract is the stage where that happens. The symbol resolver isn't part of the rule engine: it's a service the engine, the assemblers and the graph builder all ask.

02The stages, in order

Eight stages run one after another. What makes them fit together is what each one leaves in memory for the next.

Why assemble runs before flows

The stages run in this order: parse, extract, assemble, flows (the whole application), write. Flows must come after assemble because it needs completed facts, such as an endpoint's full path, to name each flow.

04What ast-grep sees

ast-grep parses a file into a syntax tree and finds the subtrees that fit a pattern. It knows shape. It knows nothing about meaning.

The pattern $TASKS.add_task($FN $$$) means: an attribute call named add_task on anything (call it TASKS), whose first argument is anything (call it FN), followed by any other arguments. On apps/backend/app/api/routers/job.py it finds this, with the captures highlighted:

# job.py, line 28
background_tasks.add_task(svc.run_project_jobs, project_id)
#      $TASKS                     $FN                   $$$

What ast-grep hands over

The match's file and line, and each capture as a piece of source text: TASKS = "background_tasks", FN = "svc.run_project_jobs".

What it can't tell you

Whether background_tasks is FastAPI's BackgroundTasks or some other object with an add_task method, and which function svc.run_project_jobs is. Those words get their meaning from a parameter annotation and an import elsewhere. That's the resolver's job.

Patterns can be broad on purpose. httpx-client-call's pattern $CLIENT.$VERB($URL $$$) matches 246 places in Contextualized, every .get(…) on a dict included. Only 24 are httpx calls. The rule's where clause, checked by the resolver, throws the other 222 away.

05Anatomy of a rule

Three blocks, each handled by a different part. Reading a rule is knowing who reads which block.

# rule-packs/python/steno-pack-fastapi/rules/fastapi-endpoint.yaml
id: fastapi-endpoint
match:                                 # read by ast-grep: the shape
  rule:
    kind: decorated_definition
    has:
      kind: decorator
      has:
        pattern: $ROUTER.$METHOD($PATH $$$)
  constraints:
    METHOD: { regex: "^(get|post|put|patch|delete)$" }
    PATH: { kind: string }
where:                                 # read by the engine, answered by the resolver
  $ROUTER: { type: [fastapi.APIRouter, fastapi.FastAPI] }
emit:                                  # read by the engine: what it means
  - node: [Interface, HttpEndpoint]
    as: endpoint
    method: $METHOD                    # a value → its text ("post", uppercased)
    path: $PATH                        # a value → value_of → "/projects/{project_id}"
    prefixed_by: $ROUTER               # a symbol → symbol_of → app.api.routers.job.router
  - edge: EXPOSES
    from: "@app"                       # an anchor: the application being ingested
    to: endpoint                       # the node named by `as:` above
  - entry_point:
      trigger: endpoint
      function: "@function"            # an anchor: enclosing() of the match

How the engine reads each field in emit

The engine decides by the field's role, not by what you wrote. The same $ROUTER becomes a qualified name in prefixed_by but would become a constant if it sat in path.

You writeWhereThe engine turns it intoBy asking

$Xprefixed_by, clue owner / parent / child, {Function: {symbol: $X}}a qualified name, the same everywhere the object is used. If it can't be found, the whole emit is droppedsymbol_of
$Xclue typethe class it names; dropped if it isn't a classclass_of
"@function", "@class", "@file"anywherethe function, class or file the match sits inenclosing
"@app"edge endthe application whose module contains the file, decided later in flowsthe graph builder

06Life of one match

In the extract stage, the rule engine runs each rule over each file. For every match ast-grep finds, five things happen.

The same five steps, on fastapi-background-task

  1. ast-grep matches job.py line 28, capturing TASKS = background_tasks and FN = svc.run_project_jobs.
  2. Scope. enclosing(job.py, 28) → function app.api.routers.job.run_project_jobs, no class. The scope is that module plus that function.
  3. Captures. Each capture's text is parsed by Python's ast: Name("background_tasks"), and Attribute(value=Name("svc"), attr="run_project_jobs").
  4. where $TASKS: {type: [fastapi.BackgroundTasks, …]}. type_of(background_tasks) → fastapi.BackgroundTasks, from the parameter annotation through the import. It passes.
  5. emit an INVOKES edge. from: "@function" → run_project_jobs. to: {Function: {symbol: $FN}} → symbol_of(svc.run_project_jobs): svc isn't a module or class, so the resolver asks type_of(svc) → app.services.job.JobService and finds the method → app.services.job.JobService.run_project_jobs. Property async: true is a literal.

Config rules run before all code rules, so their property clues can feed value_of. No pack ships a config rule today, so that step does nothing yet (see What I noticed).

What comes out: three kinds

A rule doesn't decide whether it's producing a "fact" or a "clue". It reports what it sees, and that's one of three kinds:

KindExampleDone?
FactClass Job maps to table jobyes goes on to the graph as it is
Fact with a blankEndpoint POST /projects/{project_id}, prefixed by routernot yet its full path waits for the router's prefixes
Cluerouter has prefix /jobsnever stored a note that fills another fact's blank

The assemble stage (section 09) fills in the blanks. Why not find the clues first? No single file has the whole story, and files can be read in any order: the endpoint and its router's prefix are in job.py, the /api mount is in __init__.py. Collecting everything first and combining afterwards works whatever order things are found in, and rules never have to know about each other.

07Rules, resolver, assemblers

They all work on the same code, but each answers a different kind of question. The fastest way to keep them apart is to ask who answers what.

A rule

YAML · one per framework pattern · you write it

Knows that a shape means something: "@router.post(path) on a function is an endpoint and the start of a flow."

Doesn't know what any name refers to. It names what it needs (a type, a symbol, a value) and lets the engine ask.

The symbol resolver

Python code · one per language · Steno core

Knows what names mean: imports, annotations, assignments, self.x, base classes, call sites.

Knows nothing about FastAPI or SQLAlchemy. It answers questions about any code and never decides what a fact is.

The assemblers

Python code · one per clue type · Steno core

Know how to combine facts that no single match could see: a prefix in one file, a mount in another, an endpoint in a third.

Language-agnostic: they join on the qualified names the resolver produced.

Why the split matters

Adding a framework means writing rules, never touching the resolver. Adding a language means writing a resolver (Java's will be the JVM helper) and rules, never touching the assemblers or the graph. That's how the graph stays language-agnostic.

08The resolver's questions

At the start of parse the resolver reads every non-test .py file once into an index: modules, their imports, classes, functions, parameters and annotations, and module values kept as unevaluated code. Nothing is resolved up front. Each question is answered when asked, by asking smaller ones.

Module names come from source roots: every folder with a pyproject.toml, setup.py, setup.cfg or requirements*.txt. Contextualized's are the repository root and apps/backend, so apps/backend/app/api/routers/job.py is app.api.routers.job, the same name its own imports use. Most questions take an expression and a scope (the module and function it appears in), because the same name means different things in different functions. All outputs below are real.

enclosing(file, line)

→ the function and class that contain a line

Asked by

The engine, once per match. Supplies the scope and the @function / @class anchors.

Examples
enclosing(api/routers/job.py, 16) → app.api.routers.job.run_project_jobs, no class Line 16 is the @router.post decorator; a function's span starts at its first decorator. enclosing(api/routers/job.py, 13) → no function, no class router = APIRouter(prefix="/jobs") is module-level code.

symbol_of(expr, scope)

→ the qualified name an expression refers to

Asked by

The engine for symbol fields; the call graph for every call. Clue labels and stable IDs depend on it.

How

A name: a local or parameter → this module's definitions → imports (through re-exports) → builtins. a.b: through a module, a class, or the type of a.

Examples
symbol_of(job_router) in app.api.routers → app.api.routers.job.router An import alias: from .job import router as job_router. symbol_of(svc.run_project_jobs) in job.run_project_jobs → app.services.job.JobService.run_project_jobs symbol_of(project_id) in job.run_project_jobs → app.api.routers.job.run_project_jobs.<locals>.project_id A parameter gets a local name, so it never collides with anything elsewhere.

type_of(expr, scope)

→ the type of the value an expression produces, or nothing

Asked by

where: type checks, symbol_of on attributes, table_of, the client assembler.

How

self → its class; a parameter → its annotation; x = Cls() → Cls; x = f() → f's return annotation; with f() as x → what f yields; self.x → how the class set it; a library method → a returns hint from a client clue.

Examples
type_of(svc) in job.run_project_jobs → app.services.job.JobService type_of(router) in app.api.routers.job → fastapi.APIRouter type_of(session) in JobService.create_job → sqlalchemy.ext.asyncio.AsyncSession From async with get_async_db_session_context() as session, annotated -> AsyncGenerator[AsyncSession, None]. type_of(job) in DiffTaskService (job = await session.get(DiffTask, id)) → None The type depends on an argument, which the resolver doesn't follow. A known gap, with real cost (section 13).

class_of(expr, scope)

→ the class an expression names (a class, not an instance)

Asked by

where: class checks on constructors, clue type fields, table_of.

Examples
class_of(JobService) in job.run_project_jobs → app.services.job.JobService class_of(svc) in job.run_project_jobs → None svc is an instance. Use type_of for that.

value_of(expr, scope)

→ the constant an expression evaluates to, or UNRESOLVED

Asked by

The engine, for every ordinary value field in an emit.

How

Literals; f-strings and +; a local assigned once; module constants, also through imports; class defaults; os.getenv(key, default). A function parameter inside a string becomes {name}.

Examples
value_of(os.getenv("OLLAMA_BASE_URL", settings.OLLAMA_LOCAL_HOST_URL) + "/api/tags") → "http://localhost:11434/api/tags" No config sets the key, so the default is used: the Settings class declares the attribute with that default. value_of(detail_url) in JiraDataProvider.get_linked_pull_requests → UNRESOLVED Built from self.url, which comes from a database row: known only at runtime.

is_subclass(type, targets)

→ true if the type is a target or inherits from one

Asked by

Every where check and the client assembler.

Why

So a rule about a library class also catches the app's own subclass of it. Repository base classes are walked; library bases are compared by name only.

invocations(function)

→ every first-party call in a function, in source order

Asked by

The graph builder, once for every function in the repository.

How

Walks the body including closures, resolves each call target with symbol_of, keeps calls into repository functions (a class call counts as its __init__), and flags calls inside if/try as conditional and inside loops as in-loop.

Examples
invocations(app.services.job.JobService.run_project_jobs) → app.core.relational_db.get_async_db_session_context line 88 → app.services.data_source.DataSourceService.aget_project_data_sources line 91 → app.services.job.JobService.run_data_source_job line 99 invocations(app.api.routers.job.run_project_jobs) → none The handler passes svc.run_project_jobs to add_task; it never calls it. Only the background-task rule connects them.

09The assemble stage

After extract, the Extraction holds facts with blanks and the clues that fill them (section 06). Assemble runs six steps over it, always in this order, then writes the facts JSON.

  1. Deduplicate clues. The same prefix seen twice counts once.
  2. Prefix chains. For each node with a pending prefixed_by, walk its owner's prefix and mount clues up to the top and prepend them to path.
  3. table_of. Collect every Entity -MAPS_TO-> Table the model rule emitted. For each placeholder, find the entity behind the expression (class_of, else type_of) and swap in its table; if there is none, drop the edge.
  4. Clients. Register each client clue's returns hints with the resolver, then visit every receiver.method(…) call in the repository: if type_of(receiver) is a subclass of a clue's type, the method becomes CALLS (for an ExternalSystem) or READS_FROM/WRITES_TO per operations.
  5. Partial references. A reference like {DataStore: {vendor: chroma}} becomes the app's one node that matches; several matches mark the edge ambiguous; none leaves it to become a stub.
  6. Deduplicate edges. Same type, same ends, same properties: kept once.

10The flows stage

Facts become a graph plan here. The builder runs five steps, each adding to one in-memory plan keyed by stable ID.

  1. Structure. Every folder with a build file is a Module. A module containing an entry point is a :Service and gets an Application. Contextualized: ., apps/backend (Service → application contextualized-backend), apps/frontend/app.
  2. Fact nodes. Each extracted node gets its ID: endpoints and entities under their application, tables under a placeholder relational store for the space, external systems by host (or unresolved).
  3. Fact edges. Each extracted edge, with @app replaced by the application that owns the file.
  4. Code. invocations for all 486 functions builds the call graph; async edges from rules are added. Everything reachable from an entry point becomes a Function node (274), with INVOKES edges carrying seq, line, conditional and in-loop. A function is tagged significant when it, or anything below it, reads, writes or calls out.
  5. Flows. One Flow per entry point: STARTS from the endpoint, ENTRY into the handler, and every effect of every function it reaches copied onto the flow as a rollup edge.

One flow, as it lands in the graph

Rules that add async edges change flows a lot. POST /api/data/sources/ reaches 18 functions through ordinary calls and 38 once the background tasks it starts are followed.

12One endpoint, end to end

POST /api/jobs/projects/{project_id}, from source to Neo4j, with the stage each step happens in.

  1. cloneThe repository lands in /tmp/steno-workspaces/job-N/.
  2. parsefastapi is in requirements.txt, so steno-pack-fastapi is on. The resolver indexes 112 modules; job.py becomes app.api.routers.job.
  3. extractfastapi-router-prefix matches router = APIRouter(prefix="/jobs") and pins a prefix clue on app.api.routers.job.router. Same for /api on app_router.
  4. extractfastapi-include-router pins mount clues: job.router inside app_router, app_router inside the app.
  5. extractfastapi-endpoint matches line 16. where: type_of(router) is fastapi.APIRouter. Emits an HttpEndpoint POST /projects/{project_id} pending its prefix, an EXPOSES from @app, and an entry point into run_project_jobs.
  6. extractfastapi-background-task matches line 28 and emits an async INVOKES to JobService.run_project_jobs.
  7. assembleThe prefix chain makes the path /api/jobs/projects/{project_id}.
  8. flowsapps/backend holds entry points, so it's a Service; the application is contextualized-backend.
  9. flowsThe call graph, plus the async edge, reaches 22 functions. Their effects roll up: reads of data_source, diff_task, embed_task, job; writes to job and record_lock.
  10. writeMERGE (n:Interface {id: "endpoint:contextualized-backend:POST:/api/jobs/projects/{project_id}"}), then the Flow, 22 Functions, and their edges.

13What I noticed

Things found while tracing this page that are worth a decision or a fix. Each was checked against the code and the Contextualized run.

misses facts

12 real database writes are dropped

table_of needs the type of the object being saved. It's missing when the object came from a method with no return annotation (conversation = await self.get_conversation(id)), from session.get(DiffTask, id), or from a loop over a relationship (for pd in ds.project_data: self.db.delete(pd)). 6 session.add and 6 session.delete matches are lost this way, so those flows under-report their writes.

resolvers/python.py type_of · conversation.py:174, diff_task.py:123, data_source.py:420

view effect

Every unknown URL becomes the same ExternalSystem

22 of the 24 CALLS in Contextualized have unresolved URLs (Jira, Confluence, GitHub and Bitbucket, all built from a database row). They all land on one node, external:unresolved, so the views show one system that half the app calls. Grouping by the calling class or the rule, or keeping them as separate stubs, would read more truthfully.

graph/build.py _external

no effect

The pydantic-settings pack's clues are never used

It emits 62 property clues in Contextualized (11 in Steno). The engine copies property clues into the resolver only before code rules run, and only config rules' clues exist then; this pack is a code rule. settings.X resolves anyway, through the Settings class defaults, so today the pack only adds to clue counts.

extraction/engine.py extract

doc gap

Config values don't feed resolution

rule-packs.md §5 says every config key becomes a property clue automatically. That isn't built, and no pack has a config rule, so os.getenv("OLLAMA_BASE_URL", …) always uses its code default even if a .env in the repository sets it.

source/config_files.py (only used by config rules)

ordering

where can't see returns hints

The engine checks where at match time, in extract (rule-packs.md §2 says so). A client clue's returns hints are registered later, during assemble, so a where: type on a value returned by an SDK method can't see them.

extraction/engine.py _where · assemblers/assemble.py _clients

view effect

Background tasks always draw as the last step

An INVOKES that exists only because of a rule (an add_task) has no seq, and the flow view sorts calls without one to the end. A task added in the middle of a handler still appears after everything else it calls. (Edges that the call graph also sees, like asyncio.create_task(f()), do get a seq.)

graph/build.py _fact_edge · graph/views.py flow

coverage

Only HTTP endpoints start flows

Every entry point comes from fastapi-endpoint. Steno ingesting itself gets 25 flows, all Admin API routes; its worker loop, the most important code path, isn't a flow because nothing marks a CLI command or a polling loop as an entry point.

minor

The flow view stops at 12 hops

The builder follows calls without a limit; the view re-walks INVOKES*0..12. Contextualized's deepest chain is 7, so nothing is cut today, but a deeper app would show fewer steps than the flow's functions count.

graph/views.py flow
