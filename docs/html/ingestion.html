How a repository becomes a graph

Ingestion runs eight stages in order. This page starts with all of them on one screen, then takes each stage apart: what it reads, what it does step by step, and what it leaves behind for the next one. Two parts that aren't stages get their own sections, because everything leans on them: the symbol resolver, and how Postgres and Neo4j stay in step.

Every example is real output from running Steno on Contextualized at commit ac93a3b: 190 files, 112 Python modules, 486 functions, 9 rule packs, 33 endpoints, 33 flows. Timings are one run on a laptop.

Why assemble runs before flows

Flows names each flow after its trigger, such as POST /api/jobs/projects/{project_id}. That full path only exists after assemble has added the router prefixes, so flows has to wait for it.

02How a job gets run

Ingestion doesn't run inside the API. Asking for a run only adds a row to a Postgres table; a separate worker process picks it up. The table is the queue: there's no message broker (D35).

  1. Asking for a run. The UI's Run button calls POST /api/jobs with a repository and a mode (make dry-run REPO=x does the same through steno job enqueue). The API inserts a row into ingestion_job with status queued and returns at once. Nothing has run yet.
  2. Picking it up. Each worker (steno worker, started by make worker or make dev) checks the table every 2 seconds. It claims the oldest queued job with SELECT … FOR UPDATE SKIP LOCKED, sets it to running, and commits. SKIP LOCKED means a row another worker is claiming at that moment is skipped, so two workers never get the same job, and running more workers runs more jobs in parallel.
  3. Running it. The worker runs the eight stages in order (ingestion/pipeline.py). Before each stage it commits an ingestion_stage row marked running; after it, the status (succeeded, skipped or failed), the seconds and the metrics. Committing each row as it goes is what lets the UI show progress live: the Jobs page asks GET /api/jobs/{id} every 2 seconds.
  4. Finishing. If every stage succeeds or is skipped, the job is succeeded. If a stage raises an error, that stage is failed, later stages don't run, and the job is failed with the error message. Either way the clone folder is deleted. Stopping a worker (Ctrl+C) lets the current job finish first.
ModeWhat it does
dry_runEvery stage, including write: the graph is real. Only LLM text is skipped; the cards stage will report what it would have cost (D26).
fullThe same, plus LLM cards once they're built
nightly (a trigger, not a mode)Each night workers queue a full run for every repository whose branch moved since last_ingested_sha (STENO_NIGHTLY_AT, UTC; steno job nightly by hand). Every run analyzes the whole repository and writes only what changed (D59).

Queries stay fast

Parsing a repository is heavy. In its own process it never slows the API or MCP tools.

Scales by adding workers

More steno worker processes, more jobs at once. No coordination beyond the row lock.

Failures stay contained

A job that crashes marks itself failed; the API and other workers carry on.

Resolve and assemble are different jobs

  • Resolve means answering what is this?. Only the symbol resolver does it. It isn't a stage: it's built during parse and then asked questions by extract, assemble and flows (section 07).
  • Assemble means filling in a fact's blanks from clues found elsewhere. The assemblers do it, in the assemble stage (section 08). For the hard parts they ask the symbol resolver.

The units of extraction are rules in rule packs; the rule engine runs them. Nothing is called an "extractor" (DESIGN_DOC D56, D57).

04clone and deps

Stages 1–2 · ingestion/pipeline.py
ReadsThe repository row in Postgres (URL, branch, connector)
DoesA shallow git clone of the default branch
Leaves/tmp/steno-workspaces/job-N/ and the commit SHA on the job

clone fetches the code into a temporary folder that's deleted when the job ends, success or failure. Credentials come from the connector's reference into a secret store, never from Postgres itself. The commit SHA is saved on the job and stamped onto every fact later, so every node in the graph says which commit it came from.

deps exists for Java: it will download the dependency JARs so Java's symbol resolver can answer questions about library types (which send a KafkaTemplate has, what a Spring base class provides). Python's resolver recognizes library types by name from imports, so for Python the stage records itself as skipped.

05parse

Stage 3 · pipeline.parse → Engine.parse
ReadsThe clone, and every pack's pack.yaml
DoesPicks the rule packs, lists the files, builds the symbol table and the syntax trees. No rules run.
LeavesThe rule engine in memory, holding all three

Parse prepares; it never interprets. It does five things, and everything later depends on what they build. Rule packs and ast-grep both show up here, but only to decide what to prepare and to build the trees. No rule is matched until extract.

  1. Decide what to prepare, from the rule packs. Each pack says when it applies; parse checks every pack against this repository (below). The enabled packs say which languages need a symbol resolver, and which files need syntax trees: only files some rule will look at, parsed with that language's grammar. Only pack.yaml is read here; the rules inside run in extract.
  2. List the files once. Walk the clone, never entering .git, node_modules, .venv, build and similar folders. Every later step uses this list: 190 files.
  3. Find source roots. Every folder with a pyproject.toml, setup.py, setup.cfg or requirements*.txt is the root its module names start from. Contextualized's are the repository root and apps/backend, so apps/backend/app/api/routers/job.py becomes the module app.api.routers.job, the same name its own imports use.
  4. Build the symbol table. Python's ast module reads every non-test .py file and the resolver files what it finds, per module (below).
  5. Build the syntax trees. ast-grep (tree-sitter) turns every file a code rule will look at into a syntax tree: 112 of the 190 files, kept in memory. Building trees is all ast-grep does here; searching them with each rule's pattern happens in extract.

The symbol table is a table of contents, not answers

Nothing is worked out during parse. router is stored as the code APIRouter(prefix='/jobs', …), not as "an APIRouter whose prefix is /jobs". Answers are computed later, only when someone asks, by looking things up in this table (section 07). That keeps parse fast (0.16 s) and means the resolver never does work nobody needs.

Two parsers, two trees per Python file

Python's ast → the symbol table

Python's own parser. Gives exact names, imports, annotations and assignments: what the resolver needs to answer questions about meaning.

tree-sitter → ast-grep's trees

What rules match against. Works the same way for every language, which is why rules are portable.

So each Python file is read twice, once per parser. At 0.16 s for 112 modules that's cheap; it's listed as a possible optimization once a large repository shows it matters.

06extract

Stage 4 · pipeline.extract → Engine.extract
ReadsThe syntax trees, the enabled rules, the symbol resolver
DoesRuns every rule on every file. Config rules first, then code rules.
LeavesFacts, facts with blanks, and clues: 75 nodes, 230 edges, 91 clues, 33 entry points

What ast-grep sees

ast-grep finds subtrees that fit a pattern. It knows shape, nothing about meaning. The pattern $TASKS.add_task($FN $$$) means: an attribute call named add_task on anything (call it TASKS), whose first argument is anything (call it FN), followed by any other arguments. On job.py it finds:

# job.py, line 28
background_tasks.add_task(svc.run_project_jobs, project_id)
#      $TASKS                     $FN                   $$$

ast-grep hands over the file, the line and each capture as source text. It can't tell whether background_tasks is FastAPI's BackgroundTasks, or which function svc.run_project_jobs is. Those words get their meaning from an annotation and an import elsewhere: that's what the engine asks the symbol resolver.

Patterns can be broad on purpose. httpx-client-call's $CLIENT.$VERB($URL $$$) matches 246 places in Contextualized, every dict .get(…) included. Only 24 are httpx calls; the rule's where clause throws the other 222 away.

Anatomy of a rule

Three blocks, each handled by a different part.

# rule-packs/python/steno-pack-fastapi/rules/fastapi-endpoint.yaml
id: fastapi-endpoint
match:                                 # read by ast-grep: the shape
  rule:
    kind: decorated_definition
    has:
      kind: decorator
      has:
        pattern: $ROUTER.$METHOD($PATH $$$)
  constraints:
    METHOD: { regex: "^(get|post|put|patch|delete)$" }
    PATH: { kind: string }
where:                                 # read by the engine, answered by the resolver
  $ROUTER: { type: [fastapi.APIRouter, fastapi.FastAPI] }
emit:                                  # read by the engine: what it means
  - node: [Interface, HttpEndpoint]
    as: endpoint
    method: $METHOD                    # a value → its text ("post", uppercased)
    path: $PATH                        # a value → value_of → "/projects/{project_id}"
    prefixed_by: $ROUTER               # a blank: symbol_of → app.api.routers.job.router
  - edge: EXPOSES
    from: "@app"                       # an anchor: the application being ingested
    to: endpoint
  - entry_point:
      trigger: endpoint
      function: "@function"            # an anchor: enclosing() of the match

The engine reads each emit field by its role, not by what you wrote. The same $ROUTER becomes a qualified name in prefixed_by but would become a constant if it sat in path.

Life of one match

  1. ast-grep matches job.py line 28, capturing TASKS = background_tasks and FN = svc.run_project_jobs.
  2. Scope. enclosing(job.py, 28) → function app.api.routers.job.run_project_jobs, no class.
  3. Captures. Each capture's text is parsed by Python's ast into an expression the resolver can work with.
  4. where $TASKS: {type: [fastapi.BackgroundTasks, …]}. type_of(background_tasks) → fastapi.BackgroundTasks. It passes.
  5. emit an INVOKES edge from run_project_jobs to symbol_of(svc.run_project_jobs) → app.services.job.JobService.run_project_jobs, with async: true, into the in-memory call graph (it isn't written to Neo4j). (How the resolver gets that answer is drawn out in section 07.)

Config rules run before all code rules, so their property clues can feed value_of. No pack ships a config rule today, so that step does nothing yet.

What comes out: three kinds

A rule doesn't decide whether it's producing a "fact" or a "clue". It reports what it sees, and that's one of three kinds:

KindExampleDone?Contextualized
FactClass Job maps to table jobyes goes on as it ismost nodes and edges
Fact with a blankEndpoint POST /projects/{project_id}, prefixed by routernot yet waits for assemble33 prefixed_by, 142 table_of, 2 partial references
Cluerouter has prefix /jobsnever stored a note that fills a blank62 property, 13 client, 8 prefix, 8 mount

Why not find the clues first? No single file has the whole story, and files can be read in any order: the endpoint and its router's prefix are in job.py, the /api mount is in __init__.py. Collecting everything first and filling the blanks afterwards works whatever order things are found in, and rules never need to know about each other.

07How the resolver answers

Not a stage · resolvers/python.py · asked by extract, assemble and flows

Every question is answered the same way: look it up in the symbol table from parse, and if the answer depends on something else, ask a smaller question first. The answers below are drawn as the chain of questions the resolver actually asks.

Example 1 · Which function is svc.run_project_jobs?

Asked by the engine while emitting the background-task edge, in the scope of the router function:

# job.py
from app.services.job import JobService                                  # line 8
…
async def run_project_jobs(project_id: UUID, background_tasks: BackgroundTasks,

    • is svc an imported module? no
    • class_of(svc) → none svc is a parameter of this function, so it names a value, not a class.
    • type_of(svc) A parameter: its type is its annotation.
      • annotation_type(JobService)
        • symbol_of(JobService) → app.services.job.JobService Not defined in this module; the symbol table's imports say JobService → app.services.job.JobService.
      → app.services.job.JobService
    • find method run_project_jobs on JobService Look in the class's methods in the symbol table; if it's not there, walk its base classes. → found, defined on JobService itself

Step 2 · Prefix chains

Two lookups are built from the clues: owner → its prefix (8 prefix clues) and child → its parent and mount prefix (8 mount clues). For every endpoint with a pending prefixed_by, walk from that owner up through its parents, joining prefixes on the way back down. No resolver questions here: the clues already carry qualified names, which is why they line up.

Step 3 · table_of

First, collect every Entity -MAPS_TO-> Table the model rule emitted: 20 pairs, such as app.models.job.Job → job. Then, for each blank, ask the resolver which entity class is behind the expression (class_of, else type_of) and look it up.

  • WRITES_TO {table_of: job} from session.add(job), services/job.py line 53 (rule sqlalchemy-session-add)
    • class_of(job) → none an instance, not a class
    • type_of(job) → app.models.job.Job Example 2 in section 07
    • which table does app.models.job.Job map to? → job
    → JobService.create_job WRITES_TO Table job

If no entity is found, the edge is dropped with the reason table_of: not a mapped entity. 37 were dropped: 24 are string joins like ", ".join(…) that the join rule's shape also matches (correctly dropped), 12 are real writes the resolver couldn't type, because the object came from something without a type annotation.

Step 4 · Clients

The one assembler that doesn't fill a blank. A client clue says "calls on objects of this type talk to that system":

# from steno-pack-chromadb, at core/vector_db.py line 38

  type: chromadb.api.ClientAPI

The assembler first teaches the resolver the returns hints, so chained calls keep their type. Then it visits every receiver.method(…) call in the repository (1,751 of them, which is why this step takes most of assemble's 1.7 s) and asks type_of(receiver):

  • self.client.get_collection(collection_name) services/chroma.py line 77, in ChromaService.get_real_chroma_collection

Step 5 · Partial references

llama-index-chroma-read knows a retriever reads from Chroma but not which server, so it emits to: {DataStore: {vendor: chroma}}. The assembler looks for nodes with that label whose properties match. One match (the two Chroma constructors describe the same store), so the edge points at it. Several would mark the edge ambiguous; none leaves it to become a stub. The 105 tables from step 3 go through the same step and match their Table nodes.

Then: the facts JSON

Assemble ends by writing every completed fact, with the rule and file and line that produced it, plus every dropped match and its reason, to job-N-facts.json. It's the best single place to check what extraction found before anything reaches the graph. steno extract <folder> --json out.json writes the same file without a job.

09flows

Stage 6 · pipeline.flows → graph/structure.py, graph/build.py
ReadsCompleted facts, entry points, the symbol resolver, the build files
DoesDecides the graph's shape: modules, applications, flows with their traces and steps, IDs
LeavesA graph plan in memory: 513 nodes, 1,291 edges, each with a stable ID. The call graph itself is thrown away.

Facts so far are loose: "this function writes to table job". Flows fits them into one tree (organization → space → application → …) and works out which code each entry point actually runs. It's pure planning: nothing is written yet, which is why it can be tested without a database.

  1. Structure. Every folder with a build file (pyproject.toml, requirements*.txt, package.json, pom.xml, …) is a Module. A module that contains an entry point is a Service and gets an Application, named after the repository plus the folder in a monorepo. Contextualized: ., apps/backend (Service → contextualized-backend), apps/frontend/app. The application is joined to its module by BUILT_FROM.
  2. Fact nodes. Every extracted node gets its stable ID (section 10): endpoints and entities under their application, tables under a placeholder data store for the repository, external systems by host. Each gets BELONGS_TO its owner.

  4. Call graph, in memory. Ask the resolver for invocations of the functions the entry points reach, merge in the async calls rules found (background tasks), and walk from the entry points: 278 of 460 functions are reached. A call to an inherited method follows the subclass it was made on: Task.run reached through DiffTaskRunner(…).run() runs as Task.run as DiffTaskRunner, whose calls go to Diff's methods. A call to an abstract method picked at runtime goes to every implementation, marked candidate. A function is significant when it, or anything below it, reads, writes or calls out; a utility when 3 or more functions call it and nothing architectural is below it. None of this is written as nodes (D60).
  5. Flows, traces and steps. One Flow per entry point, STARTS from its trigger. Walking from the handler gives its trace: every function it calls, in order, once per call site, stored on the Flow as JSON with file and lines. A utility is listed but not expanded, and a function already expanded is listed again as a repeat. Each significant entry becomes a Step node, chained FIRST_STEP / SUBSTEP / NEXT, carrying its own effects; every effect is also copied onto the flow as a rollup edge. Effects in code no entry point reaches aren't written; they're listed as unreached_effects in the stage's metrics (29 here).
  6. Files. A File node for each file a flow runs through (46), under its module, with how many traced functions it holds.

What "schema" means in Neo4j

Neo4j has no tables to create. A node is a set of labels (:Interface:HttpEndpoint:Searchable) plus properties; an edge is a type (WRITES_TO) plus properties. Any label or property can appear without being declared. So Steno's schema lives in two places outside the database:

In documentation

Which labels and edge types exist and what they mean: docs/knowledge-graph.md. The graph builder only ever produces these.

In graph/schema.py, applied by steno graph init

The only things Neo4j enforces: a uniqueness constraint on id for each of the 17 labels, and a full-text index over name and card on :Searchable nodes. A vector index comes once the embedding model is chosen.

The write, step by step

  1. Read. Every node and edge whose repo is this repository, plus any plan node another repository wrote (a shared table, a channel), with their properties.
  2. Compare (graph/delta.py), by stable ID. A fact is changed only if something other than its provenance (job, commit, source line) or its code pointers (a step's lines; line numbers inside a trace) differs. Moving a function down a file isn't a change; editing it is (each trace entry carries a hash of the function's syntax tree).
  3. Remove the edges and nodes this repository had that the plan doesn't: they're gone from the code. Shared nodes (tables, data stores, external systems, channels) are kept, because another repository may point at them, and deleted only once nothing does.
  4. Write new and changed nodes, grouped by label set in batches of 500: MERGE (n:Flow {id: row.id}) ON CREATE SET n.first_seen = … SET n += row.props, with properties that disappeared set to null. Then new and changed edges the same way. Unchanged facts aren't touched, so they keep the commit their lines were read at.
  5. Record each change in fact_change (before and after), and for a flow whose trace changed, one row listing the functions added, removed, or modified.

Why re-running is safe

The whole write (read, removals, writes) is one Neo4j transaction, so a failed write changes nothing: the graph stays as the previous run left it. Same commit: nothing differs, so nothing is written and no fact_change rows appear. A function deleted from the code: it drops out of its flows' traces (a trace change), and if it was a step, its Step node is removed. A dry run writes the graph too; it only skips LLM text.

11Postgres and Neo4j

Postgres holds what Steno is told and what it did. Neo4j holds what it knows. They never copy each other's data wholesale; they meet at a few IDs (D33).

Road 1 · Declared: Postgres first, projected into Neo4j

The organization and its spaces are typed in by an admin. They live in Postgres (organization, space) and Neo4j gets a copy so the tree Organization → Space → Application exists before anything is ingested.

  1. The API saves the change and flushes: Postgres checks it (unique names, valid parent) but doesn't commit yet.
  2. sync_declared makes Neo4j match Postgres exactly, in one Neo4j transaction: MERGE the Organization, delete Space nodes whose row is gone, MERGE every Space, and reset each space's BELONGS_TO to its current parent.
  3. If Neo4j fails, the request fails and Postgres rolls back, so the two never disagree. steno graph init runs the same sync, to repair or rebuild.

Road 2 · Ingested: git to Neo4j, Postgres keeps the record

A job (section 02) reads the code from git and writes the facts only to Neo4j, in the write stage. Postgres gets the job's record: the ingestion_job row and one ingestion_stage row per stage, with timings and counts. It never stores the facts themselves; they can always be produced again from git.

Because of this split, Neo4j can always be rebuilt: steno graph init (constraints, organization, spaces), then one ingestion job per repository. Postgres is the part that must be backed up.
